# Postman scenario collections

The deliverable is two kinds of collection under [docs/postman/collections/](../../../docs/postman/collections/):

- **`api-mirror.postman_collection.json`** — **generated** 1:1 from `docs/openapi.yaml` by `make postmandump`. **Never hand-edit it.** Regenerate after any OpenAPI change and commit the result. It is **not** wired into a pre-push hook (so a changing API surface never blocks a push) — refresh it **manually, typically weekly**, with `make postmandump`. **Comparing operation *counts* is not enough to call it fresh**: the mirror also embeds each operation's rendered description, so a spec change that only reworded a response meaning leaves the op count identical while the mirror goes stale. Just run `make postmandump` and let git tell you. Fully automatic — every path/operation is picked up from the spec, and each request's `noauth` vs bearer is **derived from the live app** (`scripts/openapi_permissions.py:introspect_routes()`, which returns `(permissions, public)` — a route with no `current_user` dependency is public), so new routes need no hand-maintained list.
- **`scenarios/NN-name.postman_collection.json`** — **hand-authored** business-process walkthroughs. This skill is about these.

**This skill is the authoritative reference for the conventions.** The inventory of what exists is the [`scenarios/`](../../../docs/postman/collections/scenarios/) directory itself — each collection's `info.description` documents what it covers, its prerequisites, any blocked/manual steps, and its verified pass count. There is no separate plan file; read the collection descriptions for the current state.

The closest working references to copy from: [`00-bootstrap`](../../../docs/postman/collections/scenarios/00-bootstrap.postman_collection.json) (the prerequisite chain + variable capture), [`07-rbac-negatives`](../../../docs/postman/collections/scenarios/07-rbac-negatives.postman_collection.json) (per-request auth for multiple identities + denial assertions), and [`09-reviews`](../../../docs/postman/collections/scenarios/09-reviews.postman_collection.json) (a two-actor workflow end to end).

## Golden rule: every collection is verified green on a live stack before it ships

A collection that hasn't been run against the running app is not done. **Run every `make` / `docker compose` command in this skill from `backend/`** — `up` / `logs` / `resetdata` / `seedlocal` / `dbshell` / `postmandump` all live in `backend/Makefile` (from the monorepo root they'd need the `be-` prefix, e.g. `make be-seedlocal`). The repeatable recipe:

1. Bring the stack up: `make up`, wait for `/health` 200. If migrations are behind (or a `NOT NULL`-adding migration can't apply over existing rows), `make resetdata` then `make seedlocal`, then `make up` again (resetdata stops app/worker — restart them). After merging `main`, also `make seedlocal` so synced roles pick up any new permissions.
2. Write a **bash + curl verification script** in the scratchpad that mirrors the collection's request order, asserts each status, and tears its data down. Drive it with `admin@test.com` / `password123` (the `seed_local.py` `SEED_PASSWORD`; it resets on each `make seedlocal`).
3. Run it, fix, re-run until green. Record the pass count (e.g. "17/17") in the collection's `info.description`.
4. Then run it under **Newman**, which is the standard now (no host node needed — it runs from the published image):

   Use the make targets — `make newman COLL=<name>` for a standalone collection, `make newmanchained COLL=<name>` for one that needs `00-bootstrap`'s exported ids (`02`–`06`). The recipe they wrap, for reference:

   ```sh
   cd docs/postman
   docker run --rm --network host \
     -v "$PWD/collections/scenarios:/s:ro" -v "$PWD/environments:/env:ro" \
     -v "$PWD/environments:/out" \
     postman/newman:latest run /s/<coll>.postman_collection.json \
     -e /env/local.postman_environment.json --reporters cli --reporter-cli-no-banner
   ```

   The third mount is **writable on purpose** — chaining needs somewhere to export to, and the other
   two are `:ro`. Chain with `--export-environment /out/chained.json` on the producing run and
   `-e /out/chained.json` on the next; `chained.json` is scratch, do not commit it.

   `--network host` is what reaches `localhost:8000`. **Docker file sharing only covers paths under the repo** — a scratchpad or `/tmp` mount is refused (`mounts denied: … not shared from the host`), so if you need to chain collections, export the environment into a directory *inside* `docs/postman` and feed it to the next run with `--export-environment /out/chained.json` + `-e /out/chained.json`.
5. Record the pass count (e.g. "63/63") in the collection's `info.description`. **Run a green collection at least twice** — several failure modes here are order- or clock-dependent (see the session-revocation note below) and show up only on a second pass.

**Two checks `json.load` cannot do — run both before claiming a collection is green.** A collection can
be valid JSON and still be broken, because the test scripts are strings to the parser:

```sh
# 1. every exec script must parse as JavaScript. Catches an apostrophe inside a single-quoted
#    test name — the JSON is fine, the script throws at runtime.
docker run --rm -v "$PWD/collections/scenarios:/scenarios:ro" --entrypoint node postman/newman:alpine -e '
const fs=require("fs"),vm=require("vm"),path=require("path");let bad=0,n=0;
function check(s,l){if(!s.trim())return;n++;try{new vm.Script(s);}catch(e){bad++;console.log("SYNTAX",l,e.message);}}
function walk(i,f){for(const t of i){if(t.item)walk(t.item,f);for(const e of (t.event||[]))check((e.script&&e.script.exec||[]).join("\n"),f+" > "+t.name);}}
for(const f of fs.readdirSync("/scenarios").filter(f=>f.endsWith(".json"))){const d=JSON.parse(fs.readFileSync("/scenarios/"+f));walk(d.item||[],f);for(const e of (d.event||[]))check((e.script&&e.script.exec||[]).join("\n"),f);}
console.log(n+" scripts, "+bad+" syntax errors");'
```

2. **Every `{{var}}` must be declared, set somewhere, or come from the environment.** A typo'd token
   variable interpolates to empty string and the request just fails with a confusing status. Grep the
   union of `variable[].key`, `collectionVariables.set(...)` and the environment's keys against every
   `{{…}}` in the file. The only legitimate leftovers are `02`, `05` and `06` reading `group_id` /
   `model_id` / `assignment_id` / `evaluation_id` from `00-bootstrap` — confirm the bootstrap still
   exports them rather than assuming.

**`{{var}}` is NOT interpolated inside a test script** — only in url / header / body. In a script use
`pm.collectionVariables.get('run_suffix')`. An assertion comparing against `'thing-{{run_suffix}}'`
compares against that literal and fails.

**`run_suffix` belongs in the *first request's* prerequest, unconditionally** — the `04-models` idiom.
A collection-level prerequest fires before **every** request, so an unconditional set there hands each
request a different suffix: "create the same name twice → 409" then creates two different roles and
gets a 201. If you find a collection-level `if (!pm.collectionVariables.get('run_suffix'))`, the guard
is load-bearing — do not "simplify" it away; move the set to the first request instead.

**What Newman still cannot do** — two collections fail unattended *by nature*, and that is documented rather than fixed: `01-auth` (its subject **is** the emailed single-use tokens, which live only in the worker log) and `18-images` (a binary upload cannot be embedded in a collection, so the file must be picked in the GUI). Everything else is expected green. `02`–`06` read `00-bootstrap`'s exported environment, so they are green **chained after bootstrap**, not standalone. (`03` additionally logs in as `redteamer@test.com` to capture `joiner_token` for the self-service join, but its own collection auth is `{{access_token}}`, which only `00-bootstrap` exports — it still needs bootstrap.)

`zsh` evaluates a bare UUID as a math expression — run verification scripts with `bash script.sh`, not inline in the zsh shell. In bash, **`UID` is readonly** — never use it as a variable name in a verification script (assignments are silently refused and the shell's own `1000` leaks into your URLs as a 422).

## Authoring conventions

- **One collection per business process**, numbered to suggest run order. Folders (A/B/C…) are sub-flows; number requests within a folder (`1 · …`).
- **Auth.** Single-identity collection → collection-level Bearer on `{{access_token}}`, populated by a login request in Setup. **Multiple identities** (e.g. admin + annotator, or a no-token negative) → set `auth` **per request** (`{type: bearer, bearer:[{key:token, value:"{{some_token}}"}]}` or `{type: noauth}`) and leave the collection default `noauth`. See `07` / `09`.
- **Variables.** `base_url` + `run_suffix` (set once in the first prerequest via `Date.now().toString(36)`) keep re-runs collision-free. Capture every created id into a **collection variable** in the creating request's `test` script (`pm.collectionVariables.set(...)`), so later steps chain off it. Secrets and shared bootstrap ids live in the `local` **environment** ([docs/postman/environments/local.postman_environment.json](../../../docs/postman/environments/local.postman_environment.json)).
- **Self-containment.** Each collection creates what it needs and deletes it in a Teardown folder (depth-first: children before parents). Note what can't be deleted (evaluation groups have no DELETE — they leak; `run_suffix` keeps them unique).
- **Assertions.** Assert the exact status when deterministic. When the status depends on data the API can't set up (a provider error, an unreachable source state), assert `oneOf([...])` and document why in the request description — surface the gap honestly, never a false green.
- **Descriptions carry the teaching.** For frontend-facing collections, every request says what the FE does at that step ("**FE note:** …"). For others, name the required permission and the visibility rule.
- **Editing an existing collection: do not `json.dump` it back.** These files were written by different generators and hands, so they disagree on formatting (tabs vs 2 spaces, `ensure_ascii` on or off, and `01`/`04`/`05` use a compact one-line-per-object style). Re-serialising reflows the whole file into a diff nobody can review. Two safe moves: (1) **surgical string edits** for a body or an assertion; (2) **splice a rendered block** in as text when adding a whole folder or request — indent it to the file's own unit (the item array's elements sit at 2 units, their keys at 3) and re-`json.loads` before writing. Check first whether the file round-trips exactly — `json.dumps(obj, indent='\t', ensure_ascii=False) + '\n'` reproduces about half of them byte-for-byte, and those you *can* rebuild programmatically with no incidental diff.
- **Variable scope bites across collections.** `00-bootstrap` publishes its ids as **environment** variables, while a collection's own captures are **collection** variables. So `{{group_id}}` resolves in a URL either way, but `pm.collectionVariables.get('group_id')` returns `undefined` for a bootstrap-owned id — use `pm.environment.get(...)` for those. Bootstrap's `run_suffix` is collection-scoped and does **not** cross over: a collection that wants a unique suffix must set its own (e.g. a folder-local `cg_suffix`).

## Request-contract gotchas (all verified against the live app — get these wrong and you get 422/404/405)

- **`client_message_id` must be a UUID.** Generate per send: `pm.collectionVariables.set('client_msg_id', pm.variables.replaceIn('{{$randomUUID}}'))`. A non-UUID → 422.
- **Register password ≥ 12 chars.** `POST /auth/register` requires `min_length=12`; **login only checks ≥8** — a 9–11-char password 422s on register (no account created), then login reports `unknown_email`. (**These are log fields, not response bodies** — login answers the identical `401 Invalid email or password.` for an unknown address, a wrong password and a deactivated account, so it cannot be used to enumerate accounts. The distinction is only in the structured log: `auth.login.failed` with `reason="unknown_email"` = no row, `reason="inactive"` = exists-but-unverified. Assert the generic message; never a reason code.)
- **A conversation belongs to a conversation group, and the group is created under a scenario.** The normal path is `POST /scenarios/{scenario_id}/conversation-groups` with `{name, models:[{evaluation_ai_model_id}]}` — it creates the group **plus one conversation per `models` entry**; use the embedded `conversations[0].id`. **Posting that create to `/evaluations/{id}/conversation-groups` is a 405**: only list/read/update/delete stayed nested under the evaluation, so a collection written before that change fails at its fixture and every downstream id resolves to `null` (this is what broke `12-licensing` folder E). The evaluation therefore needs a scenario first — `POST /evaluations/{id}/scenarios`.
- **A `generic` provider model requires `inference_endpoint`**. `POST /ai-models` with `provider: "generic"` and no endpoint is a **400** (`MissingInferenceEndpointError`), not a 422 — the dispatch mirror gate needs somewhere to send the call. This is a *fixture* breaker: a collection whose model setup predates that rule collapses at its first request and every downstream id resolves to `null` (that is exactly how `16-task-completions` went from 28/28 to 3/28 without anyone touching it). Copy the shape `09-reviews` uses: `"inference_endpoint": "https://openrouter.ai/api/v1"`.
- **Model assignment body is `{model_id}`** (`POST /evaluations/{id}/models`), not `evaluation_ai_model_id`.
- **SSE endpoints** — `POST /chat/stream`, `.../messages`, `.../messages/{id}/regenerate`, `.../messages/{id}/continue` — return `text/event-stream`, always 200 once resolved; a provider failure arrives as an `error` event in the body. Without a model credential the assistant turn finalizes to `error` but **the user message is still `complete` and flaggable**. `continue` on an `error` reply is a 409 → assert `oneOf([200, 409])`. In curl, regenerate/continue take **`-X POST`** with no body (a bare GET → 405).
- **Flag create is owner-only.** `POST /message-flags` requires the caller to own the conversation (no break-glass on create) — so the flag author must be whoever created the conversation. A reviewer must differ from the author (no self-review → 409).
- **A group create needs a non-empty `allowed_model_ids`**. `POST /evaluation-groups` without it → 422 `Field required`; with `[]` → 422 `List should have at least 1 item`. So **a model must exist before the group** — the canonical order is now `POST /ai-models` → group (carrying that id) → `approve` → evaluation → assign. Assigning a model *outside* the group's subset is a **400** (`Model is not in the evaluation group's allowed-model subset`), and the subset fails closed when empty. The **draft** path (`POST /evaluation-groups/draft`) accepts an empty subset, but `submit` re-imposes the check (**400** `Cannot submit an incomplete group: Assign at least one allowed model.`) — so a draft-based lifecycle scenario still needs the model fixture. This one silently breaks *every* group-creating collection at its first step; if a whole collection collapses at Setup, check this first.
- **`publish` needs a playable group, so a fixture group cannot go live empty.** `POST /evaluation-groups/{id}/publish` refuses a group with no live evaluation, and one whose evaluation carries no scenario — **400** `Cannot publish an incomplete group: …`. Since evaluations may be added only from `approved` onwards, the order in any collection that publishes is `create → approve → evaluation → scenario → publish`; inserting the children after the publish (the shape `14-metrics` had) fails at the publish. Both gates now **collect every gap into one message** rather than raising on the first, so an assertion pinning the whole `detail` string must carry the full list — prefer `to.include('<the one gap you set up>')` over `to.eql(...)` unless the fixture makes the set exact.
- **Licenses are addressed by UUID, not SPDX id**. `GET /licenses/{spdx_id}` is gone; it is `GET /licenses/{license_id}` — a slug is a **422**, not a 404. Curated rows (the shipped CC/ODC/CDLA set, `created_by_id: null` + an `spdx_id`) refuse PATCH/DELETE for **everyone** (403, "managed in code"); user-authored rows have `spdx_id: null`. `PATCH /platform-settings` takes `default_license_id` (a UUID; the old `default_license` string is `extra_forbidden`), an unknown id is a **400** (not 422), and deleting the current default is a **409**. Overrides are `data_license_id`; the response's `effective_license` is an **object**, not a string.
- **A refused conversation tag is a 400, not a 422**. The body is well-formed, so it is the tag *policy* that rejects it: `Tagging is disabled for this evaluation.` (`tags_enabled: false`, checked first) or `Tag key(s) not allowed…` (`tags_restricted: true` + key outside the allow-list; an empty allow-list while restricted forbids everything). `tags_enabled` **defaults to true**, `tags_restricted` to false. Authoring rejects but the prompt fold only **drops**, so removing an allowed key leaves an already-tagged conversation still sendable — assert both halves. A duplicate tag key is 409; the allow-list caps at `MAX_TAGS` (16). `DELETE …/tag-keys/{key}` addresses the key **by name**, not by row id.
- **Notes invert the flag rule.** `POST /notes` checks group **visibility only** — no ownership predicate — so an annotator can leave a note on a red-teamer's transcript. Reads/updates/deletes are **owner-scoped**: the conversation's own owner sees `total: 0` and gets a **404** on someone else's note. `evaluation_groups:manage` lifts the read/delete scope but **not** create. The `owner` role holds no `notes:*` at all (→ 403). The entity was called `annotation` before that name was freed for per-message labels; the collection is `20-notes`.
- **Annotations invert the note rule in turn.** `POST /annotations` also checks group **visibility only**, but reads are **shared**: every holder of `annotations:read` sees every author's rows, so the conversation owner reads them (`owner` holds `annotations:read` and neither write key → 403 on create) and a foreign **delete** is **403, not 404** — shared reads already revealed the row, so 404 would lie. The **red teamer holds no annotation key at all**, so the labels on their own output are invisible to them, and so is `GET /annotation-labels`. Re-annotating identically returns **201 with the same id** (idempotent, case-insensitive for ad-hoc text), never 409. There is no `PATCH`. The collection is `23-annotations`; it needs `make syncannotationlabels` as well as `seedlocal`.
- **A permission gate fires before body validation.** A caller lacking the permission gets **403 even with an invalid or incomplete body** (verified on `POST /evaluation-groups`). So an RBAC negative does not need a valid payload — but give it one anyway, so the 403 is the *only* reason it could fail.
- **Bulk envelopes: two different duplicate rules.** A row conflicting with **already-stored** state is a per-row failure (409/404 in `results`, the batch still 200). Two rows contradicting **each other** inside one envelope are rejected at validation — an **envelope-level 422 with no `results` array** (e.g. `POST /ai-models/bulk` with a repeated `name`). `dry_run: true` runs every row and rolls back. `POST /auth/invitations/bulk` row data requires **`role_ids`**, not just `email`.
- **Account-status preconditions**. An **`invited`** account refuses a status change (**409**, "only an active or inactive account…") and a password reset (**409**, "only an active account…") — demo the toggle on a seeded *active* user and restore it. `force-logout` has no state precondition and works on `invited` too. `resend` after a `revoke` is a **200**, not a 409.
- **`GET /auth/invitations/accept` is a token *check*, not the acceptance** (the POST on the same path is the acceptance): 200 pending, 404 unknown, **410** used/revoked/expired, 422 no `token`. Handy for an unattended negative, since the 404 branch needs no emailed token.
- **`POST /ai-models/{id}/health-check`: `202` on a model with **no check in flight**, `200` when one already is.** `status_code=status.HTTP_202_ACCEPTED` on the decorator is the *default*, not a hardcode — the handler sets `response.status_code = status.HTTP_200_OK` when a fresh check is already running (`app/api/v1/ai_models.py:463-465`), and `responses=` declares that branch (`:423-426` — "A check is already in flight; the current model is returned unchanged"). So: `04-models` creates its model per run, so **202 is deterministic there — assert it exactly** (`04-models…json:213` does). Against a **pre-existing** model, `oneOf([200, 202])` is the correct assertion. ⚠ It dispatches a Celery task against the model, so **deleting that model straight afterwards makes the task fail with a `NotFoundError` in the worker log** — harmless, but do not mistake it for a real error while debugging.
- **A conversation group is capped** by the `MAX_CONVERSATION_GROUP_SIZE` setting (default **4**) — one past it is a 409. Deleting a group's **last** conversation prunes the group (404 afterwards); deleting the group cascades to its members.
- **Pagination caps `limit` at 100** (`PaginationParams`, `ge=1, le=100`) — `limit=200` is a 422. `GET /ai-models` has no name/search filter, so "this row was not created" is better asserted by re-creating it (expecting 201) than by scanning a page.
- **`POST /evaluation-groups/{id}/request-changes` takes no request body**; `reject` requires `{rejection_reason}`.

## Preconditions the API can't satisfy (document them; don't fake them)

- **Emailed single-use tokens** (verify / password-reset / invitation accept) are logged by the **worker**, never returned. Mark the step `⚠ manual token` and describe: `make logs` → find `email.sent.console` to the address → copy `token=…` → paste into the variable. In a verification script, scrape it: `docker compose logs worker --no-color | grep -i "$EMAIL" | grep -oE 'verify-email\?token=[A-Za-z0-9_-]+' | tail -1 | sed -E 's#.*token=##'` (sleep ~4s first so the line is fully flushed — don't break the loop on a partial write).
- **Role ids come from `GET /roles`** (gated `roles:read`, which admin holds after `make seedlocal`) — filter `items` by `name` (e.g. `annotator`); no `dbshell` needed. To then provision a non-default role on a fresh account: `register → verify → PATCH /auth/users/{id} {role_ids:[…]} → re-login` (a pre-elevation JWT lacks the new permissions).
- **Session revocation is second-granular and inclusive — this makes ordering matter.** Force-logout (and **deactivating an account**, which also revokes) writes a Unix-second epoch to Redis, and a token is rejected when `iat <= marker` ([session_revocation.py](../../../app/core/auth/services/session_revocation.py)). A login that lands in the **same second** as a revocation therefore yields a token that is already dead — so a "this token worked before the call" baseline must not sit downstream of another revocation. `21-user-admin` orders its force-logout folder **before** the status folder for exactly this reason; reordering them makes the assertion flaky rather than wrong-looking. An admin-triggered **password reset does not** revoke sessions (verified: still 200 after 10s).
- **A notification cannot be created over HTTP** — rows are minted only by domain emitters, inside the transaction that caused them. To get one, drive a real emitter: an owner creates a group, then a **different** actor (an admin, via `evaluation_groups:manage`) runs `request-changes` / `reject`. A verdict is **skipped when the actor is the owner**, so a self-approve produces nothing — assert counts as **deltas against a baseline** read in Setup, since a seeded account accumulates notices across runs.
- **Group lifecycle is fully API-exposed** — `submit (draft→pending_approval)`, the moderation verdicts `approve` / `request-changes` / `reject`, and `publish` / `finish` all have routes, so a scenario drives `draft → … → published → inactive` (and self-service `join`, which needs `public`+`published`) deterministically with no `dbshell`. See `03`'s folders E/F/G/H. **Still gapped — evaluation level:** `POST /evaluations/{id}/approve|reject` exist, but reaching their `under_review` source has no `submit` route, so an evaluation approve/reject still needs a `make dbshell` precondition (`UPDATE evaluations SET status='under_review' WHERE id='…'`). Without that precondition the source state is deterministic, so assert the exact **409** and say why in the request description — `02` folder E does exactly this. Reach for `oneOf` only when the state genuinely cannot be forced.

## Pushing to a Postman workspace (repo → Postman, one-way)

1. Refresh the mirror if OpenAPI changed: `make postmandump`.
2. Preview (read-only, never mutates): `make postmanpushdry` — works without creds (lists local collections); with `POSTMAN_API_KEY` + `POSTMAN_WORKSPACE_ID` set it resolves each name to create-vs-update.
3. Push: `make postmanpush` — matches by `info.name`, `PUT` (stable uid/URL) if it exists else `POST`. Creds come from the environment (the target sources `.env`); they're dev-only, **not** in `Settings`. The `local` **environment is never pushed** (it carries secrets like `live_model_key`) — import it by hand once.

## When you change anything here

- **New / renamed collection** → document its scope, prerequisites, and verified pass count in its own `info.description` (the `scenarios/` directory + descriptions are the inventory).
- **Request-contract drift** (a new gotcha, a changed body) → add it to the gotchas section above so the next author doesn't re-hit it.
- This skill is registered in CLAUDE.md "Pointers" and README "Conventions" — keep those links alive.
