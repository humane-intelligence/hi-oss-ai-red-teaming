# Postman collections

Two kinds of collection live here, and they are maintained in opposite ways.

| | [`collections/api-mirror.postman_collection.json`](collections/api-mirror.postman_collection.json) | [`collections/scenarios/`](collections/scenarios/) |
|---|---|---|
| What it is | Every endpoint, 1:1 with the OpenAPI spec | Hand-authored walkthroughs of business processes |
| Where it comes from | Generated by `make postmandump` from [`docs/openapi.yaml`](../openapi.yaml) | Written by hand, verified against a running stack |
| Editing it | **Never by hand** — regenerate and commit | By hand, following the conventions in the [`postman-scenarios` skill](../../.claude/skills/postman-scenarios/SKILL.md) |
| What it answers | "What can this API do?" | "How do I actually do X, and what does the API refuse?" |

The mirror is a reference; the scenarios are the documentation. Each scenario collection's
`info.description` is its own spec — prerequisites, what it covers, what it deliberately does not, and
the assertion count it was last verified at.

## Running them

Everything runs through Newman in Docker — no Node on the host.

```bash
make up && make seedlocal        # from backend/ — a stack with the seeded roles and catalog
make newman COLL=12-licensing    # one self-contained collection
make newmanchained COLL=04-models # one that needs 00-bootstrap's exported ids first
```

`--network host` is what lets the container reach `localhost:8000`; the environment mount is writable
because chaining exports ids through it. The raw `docker run` behind the targets is in the
[skill](../../.claude/skills/postman-scenarios/SKILL.md#golden-rule-every-collection-is-verified-green-on-a-live-stack-before-it-ships)
if you need to vary it.

**Standalone vs chained.** Most collections build their own fixtures and tear them down. `02`–`06`
deliberately do not: they read a shared model / group / evaluation / assignment from `00-bootstrap`,
which publishes them as **environment** variables. Run those with `newmanchained`, which runs the
bootstrap first and feeds its exported environment to the second run.

## In the Postman app

Import `collections/scenarios/*.json` plus
[`environments/local.postman_environment.json`](environments/local.postman_environment.json), then
select that environment. It carries `base_url`, the seeded logins, and the optional `live_model_key`
for the collections that call a real provider. The committed file ships with `live_model_key` empty — set a real key only in your local copy and never commit it. `environments/chained.json` is scratch written by
`newmanchained` — never commit it.

Seeded logins come from `make seedlocal`: `admin@test.com`, `owner@test.com`, `redteamer@test.com`,
`annotator@test.com`, `viewer@test.com`, all with password `password123`.

## The two that cannot run unattended

Both are documented rather than fixed, because the obstacle is real rather than incidental.

- **`01-auth`** — its subject *is* the emailed single-use token (verify / reset / invitation accept),
  and those are written to the worker log, never returned by the API. Run it in the app and paste the
  token, or scrape it: `make logs` → find `email.sent.console` for the address → copy `token=…`.
- **`18-images`** — a binary upload cannot be embedded in a collection, so the file has to be picked
  in the Postman GUI. Green there, not runnable headless.

## Keeping them honest

A collection that has not been run against the running app is not done. Before changing anything here,
read the [`postman-scenarios` skill](../../.claude/skills/postman-scenarios/SKILL.md) — it carries the
authoring conventions, the request-contract gotchas that cost real debugging time (UUID idempotency
keys, the `generic` provider's required `inference_endpoint`, the group's non-empty allowed-model
subset, second-granular session revocation), and two checks `json.load` cannot do: every test script
must parse as JavaScript, and every `{{variable}}` must be declared, set, or in the environment.

Refresh the mirror after any API change — `make postmandump`, then commit what git shows. Comparing
operation *counts* is not a freshness test: the mirror embeds each operation's description, so a
reworded response leaves the count identical and the file stale.

## Publishing to a Postman workspace

One-way, repo → Postman, matched by `info.name`:

```bash
make postmanpushdry   # read-only preview; works without credentials
make postmanpush      # needs POSTMAN_API_KEY + POSTMAN_WORKSPACE_ID in backend/.env
```

The `local` environment is **never** pushed — it carries secrets. Import it by hand once.
